## 4. Draft and navigation contract

Draft identity is the account/session, exact record, action and editor instance. Dirty means current editable persisted values differ meaningfully from the initialized/saved baseline; defaults, loaded values, viewing a record, tab/page selection and search filters are not academic drafts.

1. Opening an editor is clean. Editing then restoring the original value is clean. Initialize comparison only after the record/defaults load; date conversion, selected-only default scope, optional fields and arrays must compare to that same baseline.
2. Saving updates only the baseline for fields actually persisted by that operation. Supervisor application drafts do not save attachment bytes or final declaration: those may still need a truthful warning. Saving contact details or a rubric component must not clear or overwrite an unrelated application/metadata draft.
3. Successful commit retires the saved draft synchronously before refresh/navigation can observe the old dirty/busy state. Keep completion permission scoped to that transition; later edits or a different record must regain protection.
4. Failed save retains values, selected files where possible and the dirty baseline. A 403/409 blocks stale retry until successful latest-record review; closing/reopening cannot reset the block. Reloading latest must explain replacement of local work and must not silently remount away the draft.
5. Distinguish three paths. **Dismiss final review:** preserve the still-visible underlying editor. **Discard editor:** protect its meaningful input once, then actually dispose it. **Complete command:** clear the committed editor and publish its result once. Do not make a generic `onClose` silently stand in for all three outcomes.
6. A dialog with private inputs protects them on Cancel, X, Escape and backdrop dismissal; confirmed discard clears them. A review-only dialog has no private draft merely because the underlying form contains values. Closing a hidden/private draft must not leave invisible unsaved state.
7. One coordinator owns protection for each active editor scope. Child forms report to it, or standalone dialogs attach equivalent protection. Avoid independent nested router blockers and repeated discard prompts for the same exit. Check portal/provider ancestry rather than assuming `useRecordDraft` is effective everywhere.
8. Apply to local Back/Cancel/X, sidebar/header/notification navigation, browser Back/Forward, query-driven record changes and form/record selection. Switching between retained draft tabs is allowed if neither draft is destroyed; replacing an editor must be guarded.
9. During a write, prevent duplicate submits and prevent dismissal that would conceal an unresolved operation. Show Saving state without offering to discard an in-flight write. After completion, remove that pending protection. A retained blocked navigation needs explicit proceed/reset handling when the write settles; it must not strand a "Saving changes" dialog after success or silently discard after failure.
10. Refresh, tab/window close and external navigation use the browser's native unload warning only when warranted. Do not attempt to show a custom modal after unload has begun. Verify the native prompt separately from synthetic `beforeunload` dispatch tests.
11. Deliberate logout needs draft protection before ending the session. `App.tsx:382` currently begins logout and clears the user before route navigation, so a route blocker alone cannot protect it. Explicitly handle that shell command; do not delay forced session expiry/revocation or change authentication rules. Never replay a former account's draft/toast into a later session.
12. Background refresh or a late response for an older record must not overwrite newer edits, clear a newer busy state, publish a notice in the wrong scope or focus a dismissed dialog. Cover StrictMode effect replay and real unmount cleanup.
